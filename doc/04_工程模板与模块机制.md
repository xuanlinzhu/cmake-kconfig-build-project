# 工程模板与模块机制

## 1. 模板设计原则

CK Build 模板遵循一个核心原则：

> 流程统一，差异显式。

标准工程、STM32 工程、未来其他 MCU 工程都应该有相似的 CMake 主流程，但平台差异不要隐藏到过深的封装中。

推荐 CMakeLists 主流程：

```text
基础配置
读取 Kconfig 生成文件
读取 CK 公共 CMake 函数
声明 project
选择 profile
设置输出目录
创建主目标
平台扩展区
用户配置区
工程扫描区
应用源码 / 头文件 / 宏 / 库
平台链接修正
构建产物生成
测试配置
工程结束
```

这样后续维护多个模板时，可以快速判断：

- 哪些是所有工程都有的流程。
- 哪些是 STM32 / Linux / MCU 独有的差异。
- 用户应该在哪个区域添加自己的逻辑。

## 2. 标准工程模板

路径：

```text
template/project/standard_project
```

适合：

- 普通 C / C++ 应用。
- Linux / Windows / macOS 本机程序。
- 非 CubeMX 的小型 MCU 工程起点。
- 单元测试程序。

核心特点：

- 引入 `ck_toolchain.cmake`。
- 默认使用 `ck_profile_generic()`。
- 默认扫描当前工程源码和头文件。
- 默认扫描 Kconfig 外部模块。
- 默认扫描当前目录下一层 CMake 子目录。
- 默认不强制生成 `.bin`、`.dis`、`size`，由 Kconfig 工具链选项控制。

关键片段：

```cmake
include(ck_config.cmake)
include(${CK_TOOLS_ROOT}/ck_tools/ck_utils.cmake)
include(${CK_TOOLS_ROOT}/ck_tools/ck_toolchain.cmake)
include(${CK_TOOLS_ROOT}/ck_tools/ck_project.cmake)

project(${PRO_NAME} LANGUAGES C CXX ASM)

ck_project_begin(${PRO_NAME})
ck_profile_generic()
ck_project_set_defaults()
ck_set_output_dirs(OUTPUT_DIR "${CMAKE_BINARY_DIR}/../bin")
ck_create_target(${PRO_NAME})
```

## 3. STM32CubeMX 工程模板

路径：

```text
template/project/stm32_project
```

适合：

- STM32CubeMX 生成的 CMake 工程。
- 需要保留 CubeMX 生成内容，同时接入 CK package / Kconfig 的工程。

核心特点：

- 使用 `ck_profile_stm32()`。
- 默认输出 `.elf`。
- 默认生成 `.map`、`.bin`、`.dis`、`.size.txt`。
- 工具链文件由 `CK_CMD_CONFIGURE` 的 `-DCMAKE_TOOLCHAIN_FILE=...` 指定。
- CubeMX 生成内容通过 `add_subdirectory(cmake/stm32cubemx)` 加入。
- 对 STM32 工程使用 `plain` 链接模式，兼容 CubeMX 子工程的 `target_link_libraries()` 写法。

关键片段：

```cmake
include(ck_config.cmake)
include(${CK_TOOLS_ROOT}/ck_tools/ck_utils.cmake)
include(${CK_TOOLS_ROOT}/ck_tools/ck_project.cmake)

project(${PRO_NAME} LANGUAGES C CXX ASM)

ck_project_begin(${PRO_NAME})
ck_profile_stm32()
ck_project_set_defaults()
ck_set_output_dirs(OUTPUT_DIR "${CMAKE_BINARY_DIR}/../bin")
ck_create_target(${PRO_NAME})

add_subdirectory(cmake/stm32cubemx)
```

## 4. 标准工程和 STM32 工程的差异

| 项目 | 标准工程 | STM32CubeMX 工程 |
| --- | --- | --- |
| profile | `ck_profile_generic()` | `ck_profile_stm32()` |
| 工具链来源 | `ck_toolchain.cmake` + Kconfig.toolchain | CMake toolchain 文件 |
| 默认目标后缀 | 无 | `.elf` |
| 默认输出 bin / dis / size | 关闭 | 开启 |
| 当前目录源码扫描 | 默认开启 | 默认关闭，CubeMX 子工程负责底层源码 |
| 当前目录头文件扫描 | 默认开启 | 默认开启 |
| CubeMX 子工程 | 无 | `cmake/stm32cubemx` |
| 链接模式 | scoped / PRIVATE | plain |
| 平台链接修正 | 默认无 | 移除部分错误隐式库，添加 STM32 链接参数 |

## 5. 用户配置区怎么用

CMakeLists 中保留了用户配置区：

```cmake
# ==================================================
# 用户配置区，可根据具体工程修改
# ==================================================
# 如果某个工程需要排除额外目录，可以在扫描前追加：
# list(APPEND CK_EXCLUDE_DIRS "third_party" "generated")

# 如果某个工程需要手动追加源码、头文件或库文件，可以在这里追加：
# list(APPEND SRC_FILES "user_file.c")
# list(APPEND INCLUDE_PATH "user_include")
# list(APPEND LIB_FILES "user_lib.a")
```

推荐规则：

- 能自动扫描的源码，不要手动追加。
- 自动扫描不方便处理的文件，再手动追加。
- 需要排除的目录，统一写入 `CK_EXCLUDE_DIRS`。
- 平台相关库和链接参数，放到平台链接修正区。
- 不要把大量项目私有逻辑写进 `ck_tools/ck_project.cmake`。

## 6. 平台扩展区怎么用

平台扩展区用于放平台专有子工程。

STM32 示例：

```cmake
add_subdirectory(cmake/stm32cubemx)
```

未来其他平台可以类似处理：

```cmake
add_subdirectory(cmake/vendor_sdk)
ck_target_link_libraries(${PRO_NAME} vendor_sdk)
```

建议：

- 平台 SDK、HAL、BSP 放在平台扩展区。
- 通用业务模块放 package。
- 工程私有源码放项目目录。

## 7. 外部模块机制

外部模块通常放在：

```text
template/package/
```

示例结构：

```text
package/
├── Kconfig
├── drv_temp/
│   ├── Kconfig
│   ├── CMakeLists.txt
│   ├── drv1.c
│   └── drv1.h
├── pack_temp/
│   ├── Kconfig
│   ├── CMakeLists.txt
│   ├── pack1.c
│   └── pack1.h
└── sum_mod/
    ├── Kconfig
    ├── CMakeLists.txt
    ├── my_sum.c
    └── my_sum.h
```

工程 Kconfig 中通过外部模块区引入：

```kconfig
# CK_TOOL_EXTERNAL_START
source "$(CK_WORKSPACE_ROOT)/package/Kconfig"
# CK_TOOL_EXTERNAL_END
```

CMake 中通过下面函数扫描：

```cmake
ck_collect_kconfig_external_paths(KCONFIG_FILE "${CMAKE_CURRENT_SOURCE_DIR}/Kconfig")
```

扫描逻辑：

1. 读取工程 `Kconfig`。
2. 找到 `CK_TOOL_EXTERNAL_START` 和 `CK_TOOL_EXTERNAL_END` 之间的 source。
3. 解析 `$(CK_WORKSPACE_ROOT)` 这类变量。
4. 找到外部模块目录。
5. 调用 `set_external_path()`，把模块加入构建搜索路径。

## 8. 新增外部模块步骤

假设新增模块：

```text
package/my_driver/
```

### 8.1 创建模块目录

```text
package/my_driver/
├── Kconfig
├── CMakeLists.txt
├── my_driver.c
└── my_driver.h
```

### 8.2 编写模块 Kconfig

```kconfig
config PKG_USING_MY_DRIVER
    bool "enable my driver"
    default n
```

### 8.3 编写模块 CMakeLists

简单模块可以写：

```cmake
if(PKG_USING_MY_DRIVER)
    find_current_source_file()
    find_current_header_dir()
endif()
```

如果模块需要链接库：

```cmake
if(PKG_USING_MY_DRIVER)
    find_current_source_file()
    find_current_header_dir()
    find_current_library_file()
endif()
```

### 8.4 在 package/Kconfig 中引入模块

```kconfig
menu "packages"
source "$(CK_WORKSPACE_ROOT)/package/my_driver/Kconfig"
endmenu
```

### 8.5 在工程中打开模块

```bash
python ck_tool.py config
```

在菜单中启用 `PKG_USING_MY_DRIVER`，保存后执行：

```bash
python ck_tool.py build
python ck_tool.py make
```

## 9. 自动扫描和手动追加的关系

CK Build 同时支持自动扫描和手动追加。

自动扫描适合：

- 普通 `.c`、`.cpp`、`.s` 文件。
- 模块头文件目录。
- 模块静态库文件。
- 简单项目结构。

手动追加适合：

- 只想编译某几个文件。
- 需要排除大量示例代码。
- 目录里有平台冲突文件。
- 第三方库结构复杂。
- 需要控制源码顺序或链接顺序。

手动追加示例：

```cmake
list(APPEND SRC_FILES
    "app/user_app.c"
    "app/user_task.cpp"
)

list(APPEND INCLUDE_PATH
    "app"
    "middleware/include"
)

list(APPEND LIB_FILES
    "lib/libexample.a"
)
```

## 10. 目录排除策略

默认排除目录由 profile 决定。

通用工程默认排除：

```text
build
bin
```

STM32 工程默认排除：

```text
build
bin
cmake
Core
Drivers
```

STM32 工程排除 `Core` 和 `Drivers` 的原因是：

- CubeMX 子工程已经负责添加底层源码。
- 如果主工程再递归扫描，容易重复编译。

如果你的用户源码放在 STM32 工程根目录下的 `app/`，通常可以保留默认策略，只扫描头文件或手动追加 app 源码。

## 11. 接入其他 MCU 的建议

不建议一开始就把所有 MCU 都塞进一个巨大函数里。

推荐步骤：

1. 复制 `standard_project` 或 `stm32_project`。
2. 新增平台 toolchain 文件。
3. 在 `CMakeLists.txt` 中选择合适 profile：
   - 裸机 MCU：`ck_profile_mcu()`。
   - 类 Linux 应用：`ck_profile_linux_app()`。
4. 在平台扩展区添加厂商 SDK / BSP。
5. 在平台链接修正区添加链接脚本、系统库、启动文件修正。
6. 如果差异稳定，再考虑把重复逻辑沉淀到 `ck_project.cmake`。

这样可以避免过早抽象导致后续工程难以修改。
