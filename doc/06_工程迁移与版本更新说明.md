# 工程迁移与版本更新说明

本文档只用于说明从旧工程迁移到当前版本时需要注意的变化。除本章外，其他文档尽量不单独强调版本号。

## 1. V2 版本更新声明

CK Build 升级到 V2 后，项目定位从“功能较多的构建工具集合”收敛为“轻量级 CMake + Kconfig 工程模板”。

这次升级的重点不是增加复杂功能，而是减少隐藏逻辑，让标准工程和 STM32 工程保持相同颗粒度，同时保留关键路径可修改。

主要变化：

- Python 核心流程集中到 `ck_tools/ck_core.py`。
- 工程侧 `ck_tool.py` 只保留入口和 Hook。
- 构建命令统一放到 Kconfig 中。
- CMake 抽象只保留关键细节函数，不再使用过重的外观模式。
- 标准工程和 STM32 工程的 CMake 主流程保持相同颗粒度。
- STM32 平台差异集中在平台扩展区、链接修正区和工具查找区。
- 当前主线不再描述 GUI 能力。

## 2. 旧文档需要删除或修改的内容

旧 README 或旧文档中容易误导的点：

| 旧描述 | 当前应改为 |
| --- | --- |
| 支持 GUI 模式 | 当前主流程只维护 CLI 流程 |
| 项目编译调用 Make | 编译命令由 Kconfig 中的 `CK_CMD_BUILD` 决定，默认可用 Ninja |
| `python ck_tool.py` 进入 GUI | 无参数会打印 usage |
| CMake API 零散列函数 | 应按架构、模板流程、模块机制重新组织 |
| 中大型工程通用构建模板 | 更准确是轻量级 CMake + Kconfig 工程模板 |
| 工具路径在 Python 中写死 | 工具路径从 Kconfig 读取 |
| 标准工程和 STM32 工程流程差异较大 | 两者应保持相同主流程，只在平台扩展区体现差异 |

## 3. 迁移步骤

### 3.1 更新工程侧 `ck_tool.py`

旧工程中如果存在大量构建流程代码，应迁移到 Hook。

当前推荐结构：

```python
from ck_tools.ck_core import CKHooks, cli_main

class ProjectHooks(CKHooks):
    def before_build(self, ctx):
        pass

    def after_make(self, ctx):
        pass

if __name__ == "__main__":
    cli_main(project_dir=SCRIPT_DIR, hooks=ProjectHooks())
```

不建议继续在工程侧复制完整构建流程。

### 3.2 更新 Kconfig 顶部配置

确保 Kconfig 包含：

```kconfig
CK_TOOLS_ROOT = ../../..
CK_WORKSPACE_ROOT = ../..
CK_PROJECT_TYPE = STANDARD
CK_CMD_CONFIGURE = cmake -S . -B build -G Ninja
CK_CMD_BUILD = cmake --build build -j4
CK_CMD_CLEAN = cmake --build build --target clean
```

复制工程后重点检查：

- `CK_TOOLS_ROOT`
- `CK_WORKSPACE_ROOT`
- `CK_CMD_CONFIGURE`

### 3.3 更新 CMakeLists 主流程

推荐按当前模板重排：

```text
基础配置
include ck_config.cmake
include ck_utils.cmake
include toolchain 或 platform toolchain
include ck_project.cmake
project
ck_project_begin
profile
output dirs
target
平台扩展区
用户配置区
工程扫描区
apply sources / includes / libraries
构建产物
测试
ck_project_end
```

### 3.4 替换旧的构建产物逻辑

旧工程如果手写了 bin、dis、size、map 生成逻辑，建议改为：

```cmake
ck_target_enable_map(${PRO_NAME})
ck_find_binutils_tool(CMAKE_OBJCOPY TOOL_NAME objcopy)
ck_find_binutils_tool(CMAKE_OBJDUMP TOOL_NAME objdump)
ck_find_binutils_tool(CMAKE_SIZE TOOL_NAME size)
ck_target_generate_bin(${PRO_NAME})
ck_target_generate_disassembly(${PRO_NAME})
ck_target_generate_size(${PRO_NAME})
```

STM32 工程则使用 ARM 工具名兜底：

```cmake
ck_find_binutils_tool(CMAKE_OBJCOPY
    TOOL_NAME objcopy
    NAMES arm-none-eabi-objcopy
    FALLBACK_NAME "bin"
)
```

### 3.5 更新外部模块区

外部模块必须放在标记之间：

```kconfig
# CK_TOOL_EXTERNAL_START
source "$(CK_WORKSPACE_ROOT)/package/Kconfig"
# CK_TOOL_EXTERNAL_END
```

否则 CMake 无法自动扫描到外部模块路径。

## 4. 从旧 STM32 工程迁移

推荐保留 CubeMX 生成目录，再把 CK 模板主流程合入。

检查项：

| 检查项 | 说明 |
| --- | --- |
| toolchain 文件 | `CK_CMD_CONFIGURE` 是否指向正确的 `cmake/gcc-arm-none-eabi.cmake` |
| CubeMX 子工程 | `add_subdirectory(cmake/stm32cubemx)` 是否存在 |
| 链接脚本 | `.ld` 文件是否被 toolchain 或 CMake 正确使用 |
| 启动文件 | `.s` 文件是否参与构建 |
| 链接模式 | 是否使用 `ck_profile_stm32()`，确保兼容 plain 链接 |
| 输出文件 | 是否生成 `.elf`、`.bin`、`.dis`、`.map`、`.size.txt` |
| 隐式库问题 | Windows / MinGW 环境下是否需要 `list(REMOVE_ITEM CMAKE_C_IMPLICIT_LINK_LIBRARIES ob)` |

## 5. 从旧标准工程迁移

检查项：

| 检查项 | 说明 |
| --- | --- |
| `ck_tool.py` | 是否替换为薄入口 + Hook |
| `Kconfig` | 是否新增构建命令和路径配置 |
| `Kconfig.toolchain` | 是否正确 source |
| `CMakeLists.txt` | 是否使用统一主流程 |
| 源码扫描 | 是否调用 `ck_collect_current_sources()` |
| 外部模块 | 是否调用 `ck_collect_kconfig_external_paths()` |
| 构建产物 | 是否按需启用 bin / dis / map / size |

## 6. 版本宏迁移

如果旧工程使用 `ck_config.h` 保存版本信息，需要确认：

1. Kconfig 中开启：

```kconfig
config CK_VERSION_ENABLE
    bool "enable ck-version function"
    default y
```

2. 执行 `config` 后，`ck_config.h` 中有：

```c
#define CK_SOFTWARE_VERSION "0.0.1"
#define CK_SOFTWARE_BUILD_TIME "1970-01-01 00:00:00"
#define CK_SOFTWARE_COMMIT_HASH "0000000"
```

3. 工程位于 Git 仓库中。

4. 执行：

```bash
python ck_tool.py make
```

版本宏才会根据 Git commit 更新。

如果不需要版本宏，关闭 `CK_VERSION_ENABLE` 即可。

## 7. 迁移后验证流程

迁移完成后，按下面顺序验证：

```bash
python ck_tool.py config
python ck_tool.py build
python ck_tool.py make
```

检查：

- 是否生成 `.config`。
- 是否生成 `ck_config.cmake`。
- 是否生成 `ck_config.h`。
- build 目录是否生成成功。
- 源码、头文件、库文件扫描结果是否正确。
- 目标文件是否生成到 `bin/`。
- STM32 工程是否生成 `.elf`、`.bin`、`.dis`、`.map`、`.size.txt`。

## 8. 建议不要迁移的内容

旧工程中如果有下面内容，不建议原样保留：

- GUI 入口相关说明。
- 工具路径硬编码。
- 复制在多个工程里的 Python 构建流程。
- 过度封装的 CMake 外观函数。
- 与当前模板流程重复的 bin / dis / size 自定义命令。
- 不再使用的 Make 固定描述。

## 9. 兼容性说明

当前代码保留了一些兼容字段：

| 旧名称 | 当前等价字段 |
| --- | --- |
| `ctx.tools_root` | `ctx.ck_tools_root` |
| `ctx.workspace_root` | `ctx.ck_workspace_root` |
| `ctx.build_dir` | `ctx.ck_build_dir` |

新代码建议直接使用 `ck_` 前缀字段，表达更清楚。
