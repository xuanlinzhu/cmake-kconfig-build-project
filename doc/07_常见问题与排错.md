# 常见问题与排错

## 1. `ModuleNotFoundError: No module named 'kconfiglib'`

原因：Python 环境没有安装 Kconfig 依赖。

解决：

```bash
pip install kconfiglib
```

Windows 下如果菜单界面还报 curses 相关错误：

```bash
pip install windows-curses
```

## 2. `Kconfig symbol not found: CK_TOOLS_ROOT`

原因：工程 `Kconfig` 中没有定义 `CK_TOOLS_ROOT`，或 Kconfig 写法不符合当前模板。

检查 Kconfig 顶部是否包含：

```kconfig
CK_TOOLS_ROOT = ../../..

config CK_TOOLS_ROOT
    string
    default "$(CK_TOOLS_ROOT)"
```

## 3. 找不到 `ck_tools.ck_core`

常见原因：

- `CK_TOOLS_ROOT` 路径不对。
- 工程目录复制后层级变了，但 Kconfig 没改。
- `ck_tools` 目录不在指定路径下。

排查方法：

1. 打开工程 `Kconfig`。
2. 找到：

```text
CK_TOOLS_ROOT = ../../..
```

3. 从当前工程目录出发，确认该路径能找到：

```text
<CK_TOOLS_ROOT>/ck_tools/ck_core.py
```

## 4. `python ck_tool.py` 无参数不能进入菜单

当前命令行入口要求显式指定命令。

正确写法：

```bash
python ck_tool.py config
```

查看帮助：

```bash
python ck_tool.py help
```

## 5. 修改 Kconfig 后 CMake 没生效

原因：修改 Kconfig 定义后，没有重新生成 `ck_config.cmake`。

推荐执行：

```bash
python ck_tool.py config
python ck_tool.py build
python ck_tool.py make
```

如果只是改了源码，不需要重新 config：

```bash
python ck_tool.py make
```

## 6. CMake 仍然使用旧编译器

原因：CMake build 目录里缓存了旧 toolchain。

当前 `python ck_tool.py build` 会删除 build 目录再 configure，一般可以解决。

如果你手动执行 CMake，需要删除：

```text
build/
```

然后重新 configure。

## 7. Ninja 找不到

错误类似：

```text
CMake was unable to find a build program corresponding to "Ninja"
```

解决：

- 安装 Ninja。
- 或把 Kconfig 中的生成器改成你已有的构建工具。

例如改成 Unix Makefiles：

```text
CK_CMD_CONFIGURE = cmake -S . -B build -G "Unix Makefiles"
```

## 8. STM32 工程找不到 ARM GCC

错误可能表现为：

```text
arm-none-eabi-gcc not found
```

排查：

```bash
arm-none-eabi-gcc --version
```

如果命令不可用，需要：

- 安装 ARM GNU Toolchain。
- 把 `bin` 目录加入 PATH。
- 或在 `cmake/gcc-arm-none-eabi.cmake` 中写绝对路径。

## 9. STM32 工程没有生成 bin / dis / size

检查三点：

1. 是否使用：

```cmake
ck_profile_stm32()
```

2. 是否调用：

```cmake
ck_target_generate_bin(${PRO_NAME})
ck_target_generate_disassembly(${PRO_NAME})
ck_target_generate_size(${PRO_NAME})
```

3. 是否找到工具：

```cmake
ck_print_binutils_tools()
```

CMake 输出中应该能看到：

```text
CMAKE_OBJCOPY = ...
CMAKE_OBJDUMP = ...
CMAKE_SIZE    = ...
```

## 10. size 打印里的 filename 太长

当前 size 保存和打印逻辑使用输出目录作为工作目录，并传入目标文件名，目的是避免终端中打印完整绝对路径。

如果仍然过长，检查是否使用了新的 `ck_target_generate_size()` 实现，或者是否手动保留了旧的 size 自定义命令。

## 11. 外部模块没有被编译

按顺序检查：

### 11.1 工程 Kconfig 是否有外部模块区

```kconfig
# CK_TOOL_EXTERNAL_START
source "$(CK_WORKSPACE_ROOT)/package/Kconfig"
# CK_TOOL_EXTERNAL_END
```

### 11.2 CMakeLists 是否调用扫描函数

```cmake
ck_collect_kconfig_external_paths(KCONFIG_FILE "${CMAKE_CURRENT_SOURCE_DIR}/Kconfig")
```

### 11.3 package/Kconfig 是否 source 到具体模块

```kconfig
source "$(CK_WORKSPACE_ROOT)/package/my_driver/Kconfig"
```

### 11.4 模块是否开启

执行：

```bash
python ck_tool.py config
```

确认对应模块开关为 `y`。

### 11.5 模块 CMakeLists 是否根据开关加入源码

示例：

```cmake
if(PKG_USING_MY_DRIVER)
    find_current_source_file()
    find_current_header_dir()
endif()
```

## 12. 源码被重复编译

常见原因：

- 当前目录递归扫描了一次。
- 子目录 `CMakeLists.txt` 又添加了一次。
- 外部模块也添加了同一份源码。

处理方式：

- 把重复目录加入 `CK_EXCLUDE_DIRS`。
- 或取消某一层自动扫描。
- 保留 `ck_normalize_project_files()` 去重。

STM32 工程默认排除 `Core` 和 `Drivers`，就是为了避免 CubeMX 子工程和主工程重复添加源码。

## 13. `target_link_libraries` 报 plain / keyword signature 混用

CMake 不允许同一个 target 混用：

```cmake
target_link_libraries(target lib)
```

和：

```cmake
target_link_libraries(target PRIVATE lib)
```

STM32CubeMX 生成的 CMake 可能使用 plain signature，因此 STM32 profile 默认：

```cmake
CK_LINK_LIBRARIES_MODE = plain
```

如果你的工程遇到该问题：

- STM32 / CubeMX 工程使用 `ck_profile_stm32()`。
- 普通工程使用 `ck_profile_generic()`。
- 不要在同一个 target 上混用两种写法。

## 14. 修改项目名后输出文件还是旧名字

原因可能是：

- 修改了 Kconfig，但没执行 `config`。
- 修改了 `.config`，但没执行 `build`。
- build 缓存还在。

推荐执行：

```bash
python ck_tool.py config
python ck_tool.py build
python ck_tool.py make
```

## 15. 版本宏没有更新

检查：

1. Kconfig 中是否开启：

```text
CK_VERSION_ENABLE=y
```

2. 是否执行的是：

```bash
python ck_tool.py make
```

版本宏在 `make` 阶段更新，不是在 `config` 阶段更新。

3. 当前目录是否是 Git 仓库。

```bash
git rev-parse --short HEAD
```

4. `ck_config.h` 中是否存在版本宏。

如果版本宏不存在，先执行：

```bash
python ck_tool.py config
```

## 16. Windows 下路径包含反斜杠导致 CMake 字符串异常

`ck_config_gen.py` 会对 CMake 字符串做转义，但仍建议：

- Kconfig 中尽量使用 `/`。
- Windows 路径尽量避免直接写裸反斜杠。

推荐：

```text
D:/armgnu/bin
```

而不是：

```text
D:\armgnu\bin
```

## 17. `build` 每次都会删目录，编译变慢

这是当前核心流程的默认策略：

```text
build -> 删除旧 build 目录 -> 重新 CMake configure
```

优点：

- 减少 CMake 缓存导致的工具链错误。
- 对交叉编译模板更稳定。
- 新手复制工程后更不容易踩缓存问题。

缺点：

- configure 阶段无法增量。

日常只改源码时，不需要执行 `build`，直接执行：

```bash
python ck_tool.py make
```

## 18. 什么时候执行哪个命令

| 修改内容 | 推荐命令 |
| --- | --- |
| 只改 `.c/.cpp/.h` | `python ck_tool.py make` |
| 改 Kconfig 配置 | `config -> build -> make` |
| 改 CMakeLists | `build -> make` |
| 改 toolchain 文件 | `build -> make` |
| 改外部模块 source | `config -> build -> make` |
| 第一次复制工程 | `auto` |
| 想清理目标 | `clean` |

## 19. 如何判断是 Python、Kconfig 还是 CMake 的问题

| 现象 | 大概率问题层 |
| --- | --- |
| `ck_tool.py` 启动就报错 | Python / Kconfig 路径 |
| 找不到 `CK_TOOLS_ROOT` | Kconfig 定义 |
| 没生成 `ck_config.cmake` | config 流程 / kconfiglib |
| CMake include 失败 | `CK_TOOLS_ROOT` 或生成文件路径 |
| 编译器不对 | CMake toolchain / build 缓存 |
| 源码没加入 | CMake 扫描 / 模块开关 |
| 链接库错误 | CMake 链接配置 / 平台链接修正 |
| bin/dis/size 没生成 | binutils 工具查找 / 产物开关 |

## 20. 最小排错流程

遇到复杂问题时，建议按下面顺序重新来一遍：

```bash
python ck_tool.py config
python ck_tool.py build
python ck_tool.py make
```

然后检查：

```text
.config
ck_config.cmake
ck_config.h
build/
bin/
```

如果还是失败，再看失败发生在哪一层：

1. Python 启动阶段。
2. menuconfig 阶段。
3. 生成配置文件阶段。
4. CMake configure 阶段。
5. 编译阶段。
6. 链接阶段。
7. 构建产物生成阶段。
